# Drift — Phase 2: persistent ships

- `scripts/ships/ship_registry.gd` owns stable ship IDs, lookup and radius queries. `ship_state.gd` defines portable records: owner/design, installed parts/admin slots, double-precision galaxy position and destinations, velocity, orientation, hull, shield, cargo and current navigation mode. `ship_simulation.gd` handles precise integration and reusable approach math.
- `game.gd` retains the existing pilot controller as a local physics projection. It commits the active ship at the end of each step and at save/handoff. Parked ships advance from their records whether or not they have a scene representation. Nearby ships get transient scenes/colliders keyed by ID; distant ships still appear as chart markers. Movement orders, cargo and momentum survive control handoffs, including during hyperjump. Direct flight input no longer drives parked ships.
- The floating origin is stored in double precision. Rebasing moves projections, not authoritative parked positions or their destinations. The origin follows the pilot's physics region rather than panning across the galaxy with the camera.
- Saves write format 3 with stable active ship ID and per-ship state. v1/v2 loads generate deterministic IDs in saved fleet order, preserve the active ship's cargo and velocity and migrate any active jump. Old saves had no parked cargo or velocities to recover. The next-ID counter is saved separately from array order.
- The Fleet window now has a take-control button. `game_hud.gd` draws fleet markers from persistent coordinates. Updated `tests/flight_persistence_test.gd` and added `tests/ship_registry_test.gd`.

Verification: ten regression scripts passed, including v1/v2 migration, v3 save/reload, off-screen sub-unit movement, rebase, cargo/control handoff, and arrival/contact parity at all Phase 1 speeds. M4, 1,000 systems, one active ship: 0.733 ms per gameplay tick and 0.557 ms synchronous presentation in the headless baseline. A query currently scans the registry; distant movement uses the same parked navigation but does not run detailed hull contacts outside the local bubble. Enemy waves/projectiles remain transient scenario state, and manual targeting/weapon effects are not persisted. Order queues and repeat behavior are Phase 4 work.

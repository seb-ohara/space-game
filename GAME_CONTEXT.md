# Drift — game context and current implementation

*Codebase snapshot: 24 November 2026. This document describes what is present in the project, not a promise of planned features. Values are tuning constants and may change. It is intended to be copied into another AI conversation.*

## Overview

Drift is a top-down 2D space flight prototype made in Godot 4.7 using GDScript and the GL Compatibility renderer. The player creates or loads a seeded galaxy, flies ships around a continuous large-scale world, visits generated star systems, mines asteroids, manages ships and loadouts, and can use faster travel between systems. The project combines direct piloting with RTS-style selection and movement. It has procedural astronomy and combat foundations, but it should be treated as an evolving prototype rather than a finished space simulation.

The player starts in the Sol system near a deliberately placed terrestrial world and asteroid. The galaxy, its stars, systems and asteroid sites are reproducible from their seed and generator version. Ship flight and the presentation of celestial bodies are designed for playability rather than consistent physical scale.

## Project map

- `project.godot`, `main.tscn`: Godot project and entry scene. The principal game node is implemented in `scripts/game.gd`.
- `scripts/home_menu.gd`, `galaxy_preview.gd`, `galaxy_cloud.gd` and its shader: menus, galaxy creation and preview.
- `scripts/galaxy_generator.gd`: seeded galaxy, stellar properties, planetary formation and asteroid-site generation, including compatibility with older generation versions.
- `scripts/solar_system.gd`, `celestial_body.gdshader`: star/planet/moon presentation, orbital positions and zoom-dependent visualization.
- `scripts/game.gd`: game-state orchestration, flight, fleet, camera, scene ownership and much of the world rendering. It remains the owner of shared game state and scene nodes.
- `scripts/combat_controller.gd`: the combat update loop, still coupled to game-node state and helpers. `scripts/combat_damage.gd` supplies shared shield/hull damage rules without owning a ship. Targeting, AI and effects helpers remain in `game.gd`.
- `scripts/job_board.gd`, `job_board_menu.gd`, `mission_world.gd`: procedural contract ledger, in-flight Jobs menu, navigation objectives, relay trading and streamed NPC encounters.
- `scripts/mining_controller.gd`: stateless asteroid targeting, mining range and extraction rules. It receives values and returns results; the game node currently owns the player ship's mining progress, cargo, asteroid state and save data.
- `scripts/game_input.gd`: input and unhandled-input event routing. The game node forwards the Godot callbacks, and order, camera and menu helpers remain there.
- `scripts/game_hud.gd`: HUD and resource-panel drawing using the game node's canvas and state. World and tactical overlays remain in `game.gd`.
- `scripts/debug_menu.gd`, `debug_tuning.gd`: debug-build-only flight test panel, temporary tuning and speed telemetry.
- `scripts/flight_navigation.gd`: reusable, stateless navigation thrust, steering and simple move-order calculations. The game owns ship state, collision movement and order lifecycle; active-player RTS flight still has its own arrival behavior.
- `scripts/projectile_geometry.gd`: swept projectile intersections with ellipses, polygons, asteroid fields and ship hulls.
- `scripts/rocket_projectile.gd`: rocket creation and flight mechanics; the game owns projectile state, smoke and rendering.
- `scripts/asteroid_factory.gd`: deterministic asteroid shape and ore data; the game owns loading, mining and visuals.
- `scripts/ship_modules.gd`, `ship_loadout.gd`, `ship_admin.gd`, `hangar.gd`, `ship_builder.gd`, `ship_design_library.gd`: ship definitions, statistics, validation, loadouts, administration, modular construction and library.
- `scripts/ship_randomizer.gd`: seeded, class-based fine-grid hull families shared by the builder and procedural pirate encounters.
- `scripts/galaxy_saves.gd`, `settings_menu.gd`, `key_bindings.gd`: persistence, settings and controls.
- `tests/`: focused scripts for asteroid belts, navigation, game systems and controllers, ship scaling and loadouts. Assets are in directories including `ship-sprites`, `component-art`, `engine-art`, and `audio`.

## Debug test flights

In a debug build, use **F8** or **Debug** below the flight minimap to open all five tabs directly. The first click suspends the campaign in memory and creates a test flight near Sol with a copy of the active ship's design and overrides and the same galaxy seed. **Back to test flight** closes the panel and runs the test. **Return to campaign** discards the test and resumes the original flight, including unsaved progress and its previous simulation pause/rate. Test changes are never written to the campaign.

- **Flight:** tune normal speed, acceleration, turn rate, drag, boost and hyperjump; inject forward speed or spin; view current, rolling five simulation-second average and peak speed. Speed, average, peak, turn and throttle are also shown in the test HUD.
- **Blocks:** tune per-type equipment contributions where applicable. Use the Hangar to add or remove blocks or launch other designs. Existing ship overrides can take precedence over block contributions. The design library is read-only in test flights.
- **World:** change planet and moon orbital rates independently (zero freezes that orbit type in place). Star spacing changes actual world distances without scaling individual systems and applies on a fresh flight. Restarting a test preserves live tuning but resets flight progress.
- **Combat:** spawn 1–8 copies of a particular ship from the fleet, original campaign roster, design library, or built-in presets. Pick the distance, and optionally fit a laser to otherwise unarmed designs. Enemies start hostile; the panel also clears enemies and projectiles or starts random waves.
- **Actions:** refill hull/shield, ignore incoming weapon damage, empty cargo or reset live tuning. The normal simulation-rate control is still available in flight.

## Galaxy creation and stars

The new-game menu accepts a name, seed, 1–1,000 star systems (default 5, including Sol), and 3–6 spiral arms (default 4). A blank seed is randomized. Generation has a visual preview. Generator version 5 is current; versions 1–4 remain supported for existing saves and use earlier grid, spiral, cloud and wide-orbit variants.

Version 5 builds a flattened, rotating spiral cloud with a core, arm lanes, uneven concentrations and voids. A significant fraction of systems are placed in small associations around existing stars. A spatial grid and minimum spacing check reduce overlapping systems. Sol is system 0; the other positions and stellar properties are generated from named random streams derived from the seed. Older versions use different spacing and/or placement, so seed alone is not the whole identity: retain the generator version and arm count as well.

Each evolved star has a mass, age, temperature, physical radius, luminosity, metallicity, evolutionary stage, visual radius and color. Most non-Sol stars are red dwarfs; other categories include ordinary main-sequence stars, red/blue giants and supergiants, white dwarfs and neutron stars/pulsars. Luminosity follows a radius-and-temperature relationship; metallicity depends partly on galactic radius. Evolved stars can have a different formation luminosity from their present luminosity, allowing the original frost line to differ from present-day conditions. Neutron stars have radiation and pulsar properties in their generated data. These properties do not by themselves imply that every physical effect is a gameplay hazard.

## Planetary formation: simplified accretion

Current wide-orbit generations form systems with a seeded, rule-based accretion model. This is a procedural approximation, not a continuous N-body or hydrodynamic simulation.

1. A circumstellar disc extends from beyond the star to an outer radius. Its physical AU range, frost line, density, gas supply and carbon/oxygen ratio depend on the star and random stream. The frost line is approximately `2.7 × sqrt(formation luminosity)` AU. Metallicity affects solid material; pulsar fallback discs are sparse and gas-free, and most neutron stars form no planets.
2. The disc is divided into 42 radial bands containing rock and, outside the frost line, ice. Embryos form in some bands and compete for nearby material over seven growth passes. Their feeding reach increases with accumulated solids; the frost boundary limits cross-boundary feeding.
3. Embryos become rocky worlds, super-Earths, ice/ocean/carbon/lava worlds or pulsar planets according to mass, composition and conditions. Sufficiently massive icy cores can gather a shared gas reservoir and become Neptunian or gas-giant worlds. Generated worlds carry properties including mass, radius, composition, temperatures and orbital details.
4. A non-home system can produce an inward-migrating gas-rich planet. Depending on temperature and other rolls, it may become a hot Jupiter, ultra-hot Neptune or stripped chthonian core. Migration can scatter a rocky world onto a more eccentric orbit and leave a debris belt; it can also be associated with a captured moon.
5. Some residual material produces a dwarf planet and associated uncleared debris, or up to three residual belts. Planets and moons are subject to clearance checks so their orbital extents do not overlap unacceptably. Gas worlds can receive multiple moons; rocky worlds can receive one, with cratered, icy, volcanic or mineral variants.

Sol has authored anchors inside the procedural system: a one-Earth-mass terrestrial starter planet with a moon, plus a Jupiter-like giant. Other content can still be generated around these. The generator stores formation history and origin data for relevant events. Planetary period in days is estimated with a Kepler-style formula, `365.25 × AU^1.5 / sqrt(stellar mass)`; equilibrium temperature uses approximately `278 × (luminosity / AU²)^0.25` K. These are metadata and classification aids, not a guarantee that the visual orbit uses real-time physical periods.

## Scale, orbital motion and rendering

The game's world is continuous and very large, but its units combine several different conventions. A nominal AU constant is 150,000 world units; disc distances are nonlinearly compressed using a power of 2.6, and current wide versions multiply generated orbital distances by four. Stars and planets have separately tuned visual radii. Do not infer real astronomical distances or proportions directly from the screen or from the HUD speed.

The solar-system renderer updates planets and moons along elliptical orbits using eccentric anomaly and a game clock. Planet and moon visual orbit speeds use separate scale factors (0.025 and 0.075 respectively). Orbits, body markers, star names and other details change with zoom; system contents are displayed selectively to keep large views usable. The galaxy uses a cloud visualization and distant map rendering, while close-up celestial surfaces use shaders. Lighting on ships is influenced by the nearest star.

A floating origin rebases local positions when the ship gets roughly 750,000 world units from the local origin. This avoids visible precision problems at galaxy scale. The game also retains a movement remainder and special arrival tolerance to mitigate rounding. Future systems that store world-space positions should account for rebasing and saved origin, rather than assuming local coordinates never change.

## Flight and speed

The base direct-flight tuning in `game.gd` is 390 world units/s top speed, 380 world units/s² acceleration, 0.32 drag and 3.1 radians/s base turning before ship-specific factors. Ship thrust-to-mass changes speed and acceleration. Modular Main Engines use a separate, more generous normal-flight speed curve without changing boost or hyperdrive scaling. Mass, length and steering affect turning, with thrust-assisted turning for Main Engine builds. At ordinary flight speeds turning is progressively reduced, reaching 45% of the relevant turn rate at the speed limit. Angular velocity ramps rather than instantly snapping.

Movement orders drive thrust and steering. Ships drift with exponential drag when idle, so this is arcade-style inertial flight, not frictionless Newtonian spaceflight. Speed above normal limits is gradually brought down after special travel.

The HUD deliberately scales speed: it converts world units to meters using 11.25 world units per meter and then multiplies by 100 for the displayed value. For example, a base 390 world units/s reads about 3.47 km/s before ship factors. Ship administration exposes speed-related values in displayed units; displayed speeds and physical world movement must not be treated as a single literal astronomical scale.

There are two faster-travel commands. Old saves can also finish an already-active burst.
- **Sustained boost:** Toggle through the middle-click radial menu, then right-click a destination. The selected flight-capable ships boost together and keep separate formation destinations; without a selection, only the focused ship boosts. Boost can temporarily suspend each ship’s current order. The base travel speed is 6,141.25 world units/s multiplied by the ship's speed factor unless overridden in ship administration. The final approach uses a firmer braking curve to settle quickly, and cancelling boost brakes through to a stop unless another order takes over. Combat controls are cleared while using it.
- **Hyperjump:** Right-click a system on the map and select the jump action. Eligible selected ships begin their jump half a simulation second apart, with the ships furthest along the route leaving first. They physically travel to separate arrival points outside the destination system, steering, accelerating and braking rather than teleporting. On final approach, avoidance accounts for ships braking at their own slots, and a jump is complete only once the ship has settled. The default cruise speed derives from 25,500 world units/s times the ship speed factor and can be overridden. Nominal acceleration time is eight seconds. A flight-capable ship with positive speed is required; the current check does not consume a fuel resource.

Navigation brakes drift when the ship is substantially misaligned, then accelerates along its forward axis once aligned. Destination-based flight predicts conflicts with other owned ships and steers around them using temporary waypoints without changing their orders. Ships brake for occupied destinations, and local hull contacts remain the fallback. Movement and boost translate the formation together at world boundaries so separate slots do not collapse onto the same point.

## Controls, camera and fleet

Controls are strategy-only. By default, the mouse wheel zooms, Shift + left drag pans, left click/drag selects, right click issues contextual orders, and middle click opens the command wheel. Clicking empty space clears selection without interrupting travel. WASD pans the camera without affecting ship movement, Space (or F) centers and follows the selected ship, Tab cycles combat targets, and 1–5 select weapon groups. **Settings → Controls → Mouse & keyboard bindings** lets players change flight and Ship Builder controls as well as the menu/back shortcut. Actions can use keys, mouse buttons, or modifier combinations; wheel directions work for actions that don't need to be held. Bindings are saved separately from galaxy saves. Standard UI navigation is unchanged; on a Mac trackpad, a vertical two-finger swipe or pinch still zooms the map.

Fleet command pairs the ship roster with the selected ship’s cargo, current activity, upcoming orders and last result. The order composer defaults to mining until the cargo hold is full. **Start now** replaces the current order and clears the queue; **Add to queue** appends the new order. **Clear orders** cancels the current order and queue. The roster’s **Add ship** section spawns ships from available designs. Clicking an owned ship in flight or selecting its row in Fleet immediately focuses it for commands without moving the camera; no separate command button is needed. Drag-selecting a group keeps focus on the current ship if it is in the group, or focuses the first selected ship otherwise. Right-click replaces movement orders for the selection; Shift + right-click queues them. Ships keep their orders and in-progress travel when focus changes. The cargo HUD shows the first selected ship's cargo and capacity, or prompts for a selection. Fleet rows show order summaries and pending counts, with outcome notices in flight. All owned ships have persistent state and off-screen movement. Zoomed-out fleet markers give way to full, selectable hulls anywhere in the camera view, even while paused. Detailed ship contacts are still local to the active ship's physics region. Idle ships do not choose their own economic jobs.

## Ships, modules and hangar

New galaxies open the **Ship Builder** before flight; the player must build or open a flight-ready modular design and launch it. The in-flight Ship Builder opens the current modular design for editing. Its **Ship library** contains saved modular designs, and the fleet spawn list offers only the current valid modular design and saved valid modular designs. Built-in ships are no longer offered, but legacy hulls already in existing galaxies remain loadable. Designs use component dictionaries with grid/layer, connectivity, overlap and mount validation, and a 400-component maximum. The structural palette offers **Hull**, **Right-angle hull**, **Window**, and **Right-angle window**. Rotate a right-angle hull or window to fill the matching triangular half of a slot without overlapping the existing piece. Select **Hull**, then **Circle** to build a filled, pixel-art circle from square hull blocks. Drag to set its diameter or Shift-drag to resize it. Older smooth circles remain loadable. Hull shapes use a paintable neutral grey texture. Windows use continuous reflective blue glazing across joined panes, with borders only on exposed edges, and show supported equipment underneath. Structural pieces snap to a fine grid with four subdivisions per side. Each fine cell represents 0.5 m in the builder and ship library dimensions. The fine-grid workspace is 1,000 × 1,000 cells (500 × 500 m); this does not change existing flight world scaling or legacy coarse-grid coordinates. Reset view fits the current design. Engines, turret bases, and other equipment retain their original footprint sizes, but their positions now snap to the fine grid so they can line up with stepped hull edges. For engines, aim at the middle of the desired mounting edge; R changes which edge faces the hull. Click to place one piece, drag to size it, or Shift-drag to resize an existing piece. R rotates, F flips, right-drag erases, and Cmd+Z (Ctrl+Z on Windows/Linux) undoes an edit or a whole stroke. In the Interior view, fit either a one-slot **Command station** or a three-slot **Command deck** on flat hull. Existing designs remain compatible and are converted to the fine grid without changing their dimensions when opened in the builder. Hull can be placed on any free grid area. The builder saves named designs, including disconnected drafts, but launch requires a single connected ship that also passes the other flight checks. Pixel preset hulls are not editable as modular parts. The builder caches layout-derived stats and connection markers between edits and checks common rectangular hull previews without revalidating the existing ship on every drag step. The builder and fleet retain a single textured mesh for compatible hull tiles, retaining cutouts and paint. Flight merges adjacent full-cell hull collision regions into rectangles, updates the player's shield-hit glow in the hull shader without rebuilding its mesh, and hides the flight scene behind the opaque editor. Run `godot --path . --script res://tests/ship_block_benchmark.gd -- tiles` in a window to measure flight FPS, sustained shield-hit FPS, editor drag FPS, and collision shape counts for the same 225-panel design.

The exterior palette's **Decorations** section adds cosmetic **Rivets** and **Vents** over flat hull. Click for a one-cell detail, drag to size it in 0.5 m increments, or Shift-drag to resize an existing detail. Symmetry mirrors the details, and right-click erases a whole decoration without cutting the hull while a decoration tool is selected. Decorations are saved with the design and shown in flight without changing ship stats or dimensions.

The selector beside **Randomize** chooses Fighter (10–22 m), Gunship (23–35 m), Corvette (36–50 m), Frigate (55–70 m), Destroyer (71–85 m), Cruiser (86–100 m), Battleship (110 m to just under 200 m), or Capital Ship (200–300 m). Class is derived from blueprint length; lengths outside those bands are **Custom**, including manual builds above 300 m. Each class has two mirrored silhouette families with seeded variation in dimensions, taper, equipment and paint. Hull wedges follow the outline, windows cover the command area, engines sit on the open stern, and internal systems support launch-ready designs. Generated ships remain fully editable, and Undo restores the design they replaced. The editor and library show the measured class.

Module stats add mass, health, power, thrust, weapon, cargo and mining contributions. Thrust/mass determines speed and acceleration factors with caps; maneuverability incorporates mass and hull length. Adjacent same-type reactors or shields provide power bonuses. Shield generators have diminishing stacked capacity: the first contributes 60 and further contributions follow a 0.6 geometric factor; recharge depends on available positive power. Admin settings can override health, shield, cargo, speed, acceleration, turning, boost and hyperdrive values, and can change visual ship length. Preset dimensions and scale are separate from astronomical scaling.

Ship Admin is temporarily unavailable. Existing per-ship overrides and shared version snapshots remain in the save format, but launches from the editor use the built design rather than old overrides. Editor-mounted weapons and mining lasers supply hardpoints when no saved hardpoint loadout is present. The Ship Builder’s **Ship Stats** panel shows live length and width, plus acceleration, top speed, maximum low-speed rotation in degrees per second, boost speed and hyperdrive speed from the same capability profile used in flight. The save and library screens share Fleet Command’s theme; the library previews the selected design and marks it as flight-ready or a draft. Each standard Main Engine supplies 225 thrust, with diminishing returns near the speed and acceleration limits.

The active loadout has up to 32 configurable slots, four by default, with positions expressed as fractions of the hull bounds. Slot types include lasers, machine guns, rockets, railguns, mining lasers, shield capacity (+100) and shield recharge (+2/s). Legacy visible turret mounts remain in saved designs for compatibility; the active player stat path removes their turret contribution in favor of the current slot-based approach. Consult the code when changing a ship's equipment so old and current systems are not accidentally counted twice.

## Mining, resources and asteroid fields

Belts are generated from leftover formation material or other formation events. Rather than filling an entire mathematical ring with rocks, the current system creates irregular local orbital arcs with dense and sparse patches, typically targeting 250–1,000 rock sites per belt, subject to placement checks. Rock spacing uses a 500-unit minimum check. Sol also has a guaranteed starter asteroid near the starting ship. Sites are deterministic, and stable IDs allow remaining ore to be associated with the same asteroid after loading.

Left-click an asteroid to highlight it without clearing selected fleet ships. Right-click an asteroid with a mining ship selected to start with that rock, regardless of the selected weapon group; Shift + right-click queues the order. With a mixed selection, only ships with a mining laser and free cargo space get the order. **Mine asteroids** in Fleet picks the nearest deposit in the ship’s system when the order starts, including after a queued jump. When the current deposit is exhausted, the ship picks another and keeps its mining total. Mining works off-screen using the same saved ore reserves. By default it continues until the hold is full; uncheck **Until cargo hold is full** to set an iron target instead. If the system has no ore left, the order reports why it stopped. Iron, tritium and mission freight share each ship's cargo capacity. Mining retains the ore in the ship's hold. Sell iron through the Jobs menu when the ship is within range of an Exchange Relay. Defeated pirates drop collectible tritium. There is no crafting or fuel-consumption loop.

## Galactic job board

Open **Jobs** in the flight toolbar. **Available** shows up to 12 offers across Routine, Challenging and Dangerous tiers. Refresh rolls a new batch relative to the active ship's nearest system without affecting accepted contracts. **Active** holds up to six jobs; **Completed** shows the latest 16 payouts. The board pauses flight while it is open.

- **Mining:** Extract fresh iron in the named system. Any fleet ship, including an off-screen miner, can contribute. An extracted unit counts once, toward the oldest matching contract first. The ore stays in the miner's hold.
- **Exploration:** Fly the active ship within range of one to three marked signals in order. Approach each signal to scan it automatically.
- **Pirate bounty:** Visit the hideout and defeat the marked pack. Difficulty changes pirate count, hull, shields, speed and firepower. Procedural pirate hulls use Fighter, Gunship or occasional Corvette silhouettes; higher difficulty does not guarantee a larger ship. Only wanted ships from that specific contract advance it.
- **Trade / transport:** Fly to the origin Exchange Relay with enough free cargo capacity, then bring the loaded ship to the destination Freight Depot. Pickup and delivery happen automatically within range. A one-system galaxy uses separate local pickup and drop-off sites instead of a hyperjump.

**Set course** replaces the active ship's orders with the next objective, adding a hyperjump if needed. For multiple legs, return to Active and set the next course once the current step is done. **Track** only changes the HUD marker. The local exchange buys iron for two credits per unit. Credits are tracked and saved; there is no purchase market yet.

Each system has a reproducible Exchange Relay, Depot and Raider Lane. Neutral freighters and pirates are generated only around the active ship when it nears their site; there are no simulated off-screen NPC fleets. Defeated raiders and individual bounty kills persist. Remaining NPCs can respawn in their initial condition after leaving the encounter or reloading. Debug test flights have no campaign board or mission actors.

## Combat and damage

Weapon groups are laser, mining laser, machine gun, rocket and railgun. Turrets turn toward targets and must be sufficiently aimed for the relevant firing/mining behavior. Projectiles and rockets have individual travel and collision logic; rockets have ejection, ignition delay, acceleration, smoke and impact effects. Hits interact with shields and hull, with shield impact visuals and a four-second recharge delay after a hit. The project also contains enemy targeting, steering, combat, death/debris and tritium-drop logic.

`ENEMY_SHIPS_ENABLED` is still `false` for the legacy enemy-wave mode. Campaign pirate fights use local raider sites or accepted bounties instead. Visual effects include engine lighting and sound, weapon flashes, shield glow and impacts. Ships use the Short Bell exhaust: a compact white-hot flame with a warm edge and a few tiny embers. Long engine streaks are reserved for sustained boost and hyperjump.

## Simulation clock

The in-flight top-right toolbar shows a galactic date and Paused/1×/2×/5×/10× controls. The authoritative simulation clock advances in 1/60 simulated-second ticks. Accelerated rates change Godot's physics tick cadence, not `Engine.time_scale` or the size of a gameplay step. Orbits, movement, mining and combat read simulation time; camera, presentation and session play time run separately. Settings, Jobs and the Ship Builder pause simulation temporarily without changing the selected speed or manual pause state. If the engine cannot sustain the selected rate within its step budget, the calendar reports the achieved rate.

## Saves and settings

Galaxy saves use Godot's `user://galaxies` directory, one `.save` file per slot, with a temporary-file write and rename. The save includes name, seed, system count, generator version and arm count where applicable; stable ship/owner IDs, double-precision fleet positions, active ship, designs and administration, per-ship health/shields, cargo, velocity and navigation; order queues and partial execution progress; simulation time, speed, manual pause and real session play time; depleted ore and floating world origin; and the contract ledger (offers, progress, loaded freight, recent payouts, credits and defeated raiders). Galaxy layout and contents are regenerated deterministically from the saved generation parameters. Formats 1–4 still load. Format 1 opens at 1× unpaused with its prior elapsed time, formats 1–3 migrate to the current ship/queue layout, and formats 1–4 start with an empty contract ledger. The next save writes format 5. Saves happen at creation, through settings, on relevant admin changes and on window close. Projectile state, live NPC positions and damage, pilot target selection and most visual effects are not saved.

Settings include mouse and keyboard bindings and graphics/display options such as graphics quality, frame cap and VSync. They are stored separately from galaxy saves.

## Living-universe roadmap status

Phase 0 ([architecture audit and baseline](LIVING_UNIVERSE_PHASE_0.md)) and Phase 1 ([simulation clock and verification](LIVING_UNIVERSE_PHASE_1.md)) are complete. Regression coverage includes time-speed parity, ship contacts, rebasing, and legacy and current saves during hyperjump. The measured 1,000-system, one-ship prototype sustained 10× on Apple M4; this does not establish throughput for a populated galaxy or other hardware. [Phase 2](LIVING_UNIVERSE_PHASE_2.md) adds stable ownership and ship IDs, double-precision persistent ship positions, per-ship cargo, and off-screen movement independent of fleet visuals. The pilot can take control of another owned ship while the first continues its movement. Distant ships do not yet use detailed local hull contacts. [Phase 3](LIVING_UNIVERSE_PHASE_3.md) exposes one equipment-derived ship capability profile for flight, mining, cargo and task suitability. [Phase 4](LIVING_UNIVERSE_PHASE_4.md) adds persistent, player-assigned orders, including off-screen mining. The job board adds contract freight and a simple relay exchange but not the broader Phase 5 generic resource and inventory system.

## Guidance for future development

- Treat this document as a snapshot; check the actual source before changing a formula or assuming a feature is exposed in the UI.
- Preserve seed, random stream, generator-version and stable asteroid-ID compatibility when changing procedural generation or loading old games.
- Keep local versus galaxy coordinates and floating-origin rebasing explicit. Account for the intentionally different world-distance, ship-size and HUD-speed scales.
- Distinguish direct flight, charged burst, sustained boost and hyperjump; they have different acceleration and control rules.
- Ship statistics, admin overrides, legacy mounts and slot loadouts interact. Check the whole calculation path before rebalancing.
- Separate procedural metadata and visuals from implemented gameplay effects; e.g. generated radiation is not automatically a radiation-damage system, and combat code is not the same as enabled enemy spawning.

# Drift living universe — Phase 0 audit and Phase 1 plan

Audited gameplay baseline: `d8af418`. Phase 0 adds tests, a benchmark and documentation only. Phases 1–17 have not been implemented.

## Current architecture and integration points

| Concern | Current implementation | Reuse or boundary |
|---|---|---|
| Session and persistence | `main.tscn` starts `game.gd`. `home_menu.gd` generates the map and preforms systems for new games. `game.gd` starts flight, restores and snapshots live state, and handles menus, HUD wiring and settings. | Keep the coordinator and existing save entry points. `galaxy_saves.gd` owns slot files and format validation, not gameplay. |
| Coordinates and movement | Active `ship_position`, `velocity`, `heading`, angular velocity and movement-mode flags live in `game.gd`. Positions are local `Vector2` offsets from `world_origin`. The active ship retains a motion remainder for small increments. Manual flight, RTS approach, burst, sustained boost and hyperjump all ultimately advance through `_advance_player`. Fleet contact uses `CharacterBody2D.move_and_collide`; ship and asteroid contacts also have game-side resolution. | Preserve the current integration order and `flight_navigation.gd` math. Rebase and collision queries are gameplay, not cosmetic. For Phase 2, use absolute scalar pairs or region-plus-local coordinates before converting to a local `Vector2`; adding two large `Vector2` values doesn't recover precision. |
| Fleet state and orders | `fleet` is an array of dictionaries indexed by selection; the active ship is copied between a dictionary and live fields. Parked ships mix position, stats, velocity and RTS destination with collision/visual nodes. Manual input can also drive parked ships and cancel their RTS orders. Switching resets active velocity and several modes; only the active ship can currently hyperjump. | Reuse `move_order_step`, steering and braking. Don't treat current manual mirroring as autonomous order behavior. Stable IDs, node-independent state and control handoff are Phase 2 work; durable orders are Phase 4. Rebase currently shifts fleet positions but not parked `destination` values: reproduce and address before depending on cross-system RTS orders. |
| Equipment | `ship_modules.gd` defines part stats and presets; `ship_loadout.gd` normalizes administrative slots. `game.gd` builds the active cache and parked stats through `_stats_with_admin`; `_ensure_ship_cache` also builds active mount data. Legacy visible mounts on player designs are excluded from current player weapon-stat contributions. | Phase 3 should share the existing stat/slot calculation and invalidation, not add a second set of module bonuses. `flight_navigation.gd` already contains reusable movement rules. |
| Mining | `game.gd` streams asteroid nodes/data for the active ship's nearest system. `galaxy_generator.gd` and `asteroid_factory.gd` produce sites and objects with stable per-system IDs; `depleted_ore` overrides generated reserves. `_update_mining` handles firing, aim, range, turret rate and capacity and commits ore/cargo changes; `mining_controller.gd` computes target/range/extraction. Iron/tritium and fractional mining progress are active-game fields, not per-ship inventories. | Reuse extraction/capacity math; build persistent deposits and centrally commit extraction before enabling multiple off-screen miners. Don't change existing asteroid IDs or generation streams. |
| Combat and presentation | `combat_controller.gd` updates shields, weapons/projectiles and enemy movement using `game.gd` state and callbacks. Damage, rocket motion and projectile geometry have helpers. Enemy waves are disabled by default. `game_input.gd` and `game_hud.gd` are delegated handlers; `game.gd` still manages camera, visual layers, particles, UI and audio. | Continue advancing shield delays, recharge, projectile motion and gameplay cooldowns with simulation steps. Avoid scheduling HUD redraw/audio mix at each accelerated substep. Preserve timestamp consistency for gameplay-linked effects. |

### Time and save audit

- Godot's physics callback drives the current simulation (default 60 Hz). `_physics_process` advances `elapsed`, moves owned ships, updates aim/mining, runs active flight, combat and collisions, rebases, streams asteroids, collects loot, and updates effects/HUD. There is no independent scheduler or speed control. `_process` advances `play_time` and camera smoothing from frame delta. Settings and hangar disable the physics callback; play time continues, and settings silence the engine audio. RTS keyboard camera panning is currently inside the physics callback.
- `solar_system.gd` evaluates visible orbital positions from the `elapsed` argument and a generated phase/period (with tuned moon/planet factors); it does not integrate independently. The same `elapsed` is used for effect timestamps and the hyperjump arrival banner. It is not a real-world timestamp and is separate from save metadata (`saved_at`).
- File format **1** uses Godot Variant serialization and a temporary-file rename; the reader rejects other formats and unknown generator versions. Generator versions **1–5** are separate from save format. Position data includes `world_origin` and local fleet positions. Persisted data includes names, parts/admin, headings, hull/shields/delay, active velocity, global iron/tritium, ore overrides, `elapsed`, `play_time`, and optional active jump destination/arrival/distance. Maps regenerate; system details load lazily when not preformed. Older files may omit origin and/or play time; preserve current fallback behavior.
- Parked velocities and RTS orders, sustained boost state, mining progress, live enemies/projectiles and most transient effects are not saved. Jump travel resumes from the saved position/velocity but resets the jump timer; do not interpret that timer as elapsed travel across a reload. Avoid extending this save scope until the corresponding ship/order phases unless required for Phase 1 parity.

## Baseline performance

Apple M4 (arm64), Godot `4.7.2.stable`, headless, generator v5, seed `7419`. Values in milliseconds; medians over three runs. Flight initialization uses preformed contents as on new-game entry, excludes map/formation time, and includes building the active flight scene. Flight tick is the median of three means over 180 moving RTS steps at 1/60 simulated seconds, after 30 warm-up steps. One starter ship, graphics quality 2, muted audio, enemy spawning disabled. This measures the current callback and synchronous redraw setup, not actual GPU rendering, frame rate, physics-server scheduling between ticks, or load behavior for many active ships.

| Systems | Map | Form all systems | Flight init | Flight tick |
|---:|---:|---:|---:|---:|
| 100 | 1.205 | 82.547 | 96.171 | 2.037 |
| 250 | 2.984 | 206.501 | 95.526 | 2.107 |
| 500 | 5.870 | 409.281 | 97.550 | 2.166 |
| 1,000 | 11.771 | 813.041 | 98.836 | 2.341 |

At 1,000 systems, ten copies of today's callback would use roughly **23.4 ms**, beyond the **16.7 ms** budget for a 60 Hz frame before any rendering. Treat 10× as gated until the accelerated path is measured. Profile synchronous presentation work (`_queue_flight_redraw`/`SolarSystem.update_view`) separately from gameplay before considering larger steps. `nearest_system` is a linear scan on cache miss, and system transitions can synchronously generate asteroid fields and replace nodes; measure that spike separately. No current baseline shows how a populated galaxy will scale.

### Regression coverage

All six existing tests pass, and the added `tests/flight_persistence_test.gd` passes. The new test exercises parked RTS movement, rebasing ship and asteroid coordinates, physical active hyperjump progress, shield delay and the separation of simulation time from play time. It saves and reloads a real slot in an isolated user-data directory, checking the fleet, active velocity, resumed jump, cargo and a restored asteroid depletion override. Existing scripts cover asteroid determinism, navigation math, projectile geometry/damage, mining extraction rules, scaling and loadouts. `navigation_thrust_test.gd` and `ship_loadout_test.gd` had Godot shutdown leak diagnostics before this work; neither flags a failed assertion. Phase 0 does not claim interactive or multi-speed coverage: the only current setting is 1×.

Run after importing assets, using `godot` or the Godot app binary:

```sh
godot --headless --path . --editor --import
for test in tests/*_test.gd; do
  godot --headless --path . --fixed-fps 60 --quit-after 300 --script "res://$test"
done
godot --headless --path . --fixed-fps 60 --quit-after 600 --script res://tests/galaxy_baseline_benchmark.gd
```

Confirm each script prints its success marker without script/assertion errors; the iteration watchdog alone does not guarantee success.

## Phase 1 implementation plan (not started)

1. **Introduce an authoritative clock and cadence.** Add a small `scripts/simulation/simulation_clock.gd` with total simulated seconds, fixed 1/60 steps, bounded pending time, pause and the requested rates (0/1/2/5/10). Use a small simulation-time interval scheduler for genuinely lower-frequency work, not a wall-clock timer and not a place to move collision or mining prematurely. Keep `Engine.time_scale` at 1. Start with one simulation second per real second at 1× and a calendar with a documented epoch, 365-day years and 24-hour days; display sub-hour detail if needed so new games visibly tick. Preserve generated orbit periods and presentation multipliers, independently of calendar formatting.
2. **Separate one precise gameplay step from presentation.** In `game.gd`, extract the existing movement/mining/combat/rebase ordering into a fixed-step method before adding extra steps per callback. Route all game-affecting deltas and timestamps to the clock; switch `solar_system.gd`'s elapsed input, combat timestamps and HUD reads without maintaining a second authoritative elapsed counter. Update camera input/smoothing, redraw submission and audio mix on real cadence. Keep asteroid availability and collision resolution in the simulation path; test that moved presentation has not altered gameplay. Cache per-system work only where profiling justifies it.
3. **Establish pause and rate controls.** Wire the in-flight HUD/top controls (`game.gd`, `game_hud.gd`, and `game_input.gd` if adding shortcuts). Settings/hangar should be independent temporary blockers, not overwrite the selected speed or unpause an explicitly paused game. A resume must not apply paused wall time. Camera and menus should remain responsive when paused; held controls and audio need explicit transition tests. Bound catch-up and expose actual achieved rate or a slowdown warning when saturated; never advance the authoritative clock for skipped work or compensate with a bigger physics delta.
4. **Persist and migrate.** Update `galaxy_saves.gd` and the game snapshot/restore methods for format 2 with a validated clock payload. Read both formats: migrate finite nonnegative v1 `elapsed`, default v1 speed to 1× and preserve the play-time fallback. Save rate and user pause state separately from temporary menu blockers and don't persist transient substep debt. Preserve generator versions, origin, asteroid IDs and the active jump payload. Handle invalid or unsupported clock payloads explicitly; test both legacy and new files without touching actual player data.
5. **Gate on parity and cost.** Add clock/scheduler tests and extend the flight regression to compare equal simulated durations at all requested rates, including orbit phases, local flight, sustained boost, hyperjump arrival, mining/cargo, shield recharge, rebase and collision contacts. Exercise crowded `CharacterBody2D` contacts: invoking multiple script substeps in one Godot physics callback may not be equivalent to separate physics-server ticks. If parity fails, adjust the integration or restrict acceleration rather than ship unreliable movement. Re-run the four-size benchmark, measure the split costs and the achieved rate with a live renderer, and stress system changes, long runs and save/load mid-jump. Do not accept Phase 1 or begin Phase 2 with a critical parity, persistence or performance issue still open.
